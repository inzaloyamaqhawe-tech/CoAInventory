# Design Principles — Why This Is Not Bolide WMS

Bolide WMS is the right tool for its job: a warehouse admin sitting at a desk,
reconciling manufacturing orders against a SQL-backed bill of materials, with a
sidebar of eight modules and a Chart.js dashboard. Chiefs of Angels' operations
tool has a different user, in a different posture, doing a different job — so it
has to look, navigate and behave differently, not just carry different branding.

## The core difference: who's holding the device, and how

| | Bolide WMS | Chiefs of Angels Inventory |
|---|---|---|
| **Primary user** | Warehouse admin, production planner | Sales associate on the shop floor, branch manager, Ops Manager on the move between stores |
| **Primary device** | Desktop / laptop, mouse + keyboard, always | Phone and tablet day-to-day on the floor; a PC in the back office or at home for the Ops Manager — the app has to be genuinely clear there too, not phone-only |
| **Primary posture** | Seated, focused session, 20+ min | Standing/interrupted on a phone; seated and reviewing on a PC — same app, two postures |
| **Navigation** | Persistent left sidebar, 8 top-level modules always visible | Bottom tab bar on phone; the *same* tabs move to a slim left icon-rail from tablet width up — never the dense, always-expanded 8-item admin sidebar WMS uses |
| **Data entry** | Typed forms, dropdowns, table edits | Tap counters, barcode/camera scan, swipe actions, voice-friendly short forms |
| **Screen density** | Dense tables, sortable columns, sticky headers | One card or one list row at a time, generous tap targets (44px+), no horizontal scroll ever |
| **Session shape** | Log in once, work for an hour | Open app for 15 seconds, do one thing (count a shelf, mark a task done), close it |
| **Visual language** | Corporate dashboard: navy/ink chrome, brand gradient accents, Chart.js line/bar charts | White ground, near-black type, a red accent pulled from the brand's own heart/tongue motifs — matched to the live chiefsofangels.co.za storefront's own palette, not an invented dark "admin" theme |
| **Offline behaviour** | Assumes always-online desktop connection | Must tolerate a dead spot in a mall basement stockroom — actions queue and sync |
| **Roles shown at once** | Same nav for every logged-in role, permissions just hide buttons | Nav itself changes shape per role — a Sales Associate's whole app is three tabs; the Ops Manager's is five plus a branch switcher |

## Concretely, what's different

1. **Mobile-first, not mobile-only.** Built and designed for the phone first, then
   the same screens and components reflow for tablet and PC — never a second,
   separate "desktop app." A Branch Manager reviewing stock on a shop iPad and an
   Ops Manager checking the leaderboard on a home PC both get a clear, full-width
   layout, not a phone screen stretched thin or a scaled-up admin dashboard. See
   [02-MOBILE-EXPERIENCE.md](02-MOBILE-EXPERIENCE.md)'s breakpoint section for
   exactly how each screen adapts.
2. **No sidebar-as-dense-admin-menu.** On phone, navigation is a bottom tab bar
   (thumb reach zone) plus a floating action button for the most common
   in-the-moment action (scan / count / new task). From tablet width up, those
   same 3–5 tabs move to a slim icon-rail on the left — compact and iconic, not
   WMS's always-expanded 8-module text sidebar.
3. **No dense tables as the primary UI, at any width.** Where WMS shows a sortable
   table with sticky headers, this app shows cards — one product, one task, one
   order per card — with the 1–2 numbers that matter in large type. On a wider
   screen those cards arrange into a multi-column grid instead of one column, so a
   PC user sees more at once — but it's still cards, never a dense grid of
   eight-column rows.
3. **Role reshapes the whole app, not just permissions.** A Sales Associate never
   sees a "branch switcher" or a company-wide leaderboard — those controls don't
   exist in their build, not just hidden buttons on a shared page.
4. **Alerts are pushed, not browsed to.** WMS's Reports page is something an admin
   goes and reads. This app puts today's alerts on the Home tab, unread-badge on
   the tab icon, and (later) as real phone push notifications — the job is to
   interrupt someone standing in a stockroom, not to wait for them to open a report.
5. **Counting and transfers are camera/tap-first.** Barcode/QR scanning for stock
   counts and receiving, large +/- steppers instead of typed quantities, swipe
   gestures for common actions (swipe a task to complete it).
6. **Built to be skimmed one-handed while distracted**, not read closely at a
   desk — short labels, icons + colour before paragraphs, confirmation via a single
   tap not a modal form.
7. **Own database, API-first from day one.** WMS reads a static JSON fixture file
   regenerated by a script. This system has its own relational database and a
   versioned REST/webhook API from the start (see
   [06-API-AND-INTEGRATIONS.md](06-API-AND-INTEGRATIONS.md)), because it's meant to
   talk to the live WooCommerce storefront, the Phase 2 VIP system, and future POS /
   accounting tools — not to be regenerated from a script before each demo.

## What's kept, deliberately

- **Role-based login** — same principle as WMS (name + PIN, not necessarily a full
  username/password on a shared shop device), just reshaped per the roles this
  business actually has (Operations Manager, Branch Manager, Sales Associate,
  Stock Controller — see [05-DATA-MODEL.md](05-DATA-MODEL.md)).
- **A live backend with real persistence**, not a static prototype — actions
  (counting stock, completing a task, actioning a transfer) really change state and
  survive a reload, the same honest standard WMS holds itself to.
- **Clear status vocabulary** — every stock movement, transfer and task has an
  explicit state machine, so nothing is ambiguous about where something stands.
